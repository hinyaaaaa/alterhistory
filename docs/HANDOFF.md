`.map` 形式の仕様は `MAP_FORMAT_SPEC.md` を見ること。ここでは重複を避け、
**未実装のもの・中途半端なもの・決めずに仮置きしたもの**だけを列挙する。

作業を始める前に、必ず `npm test` を実行して全スイートが通ることを確認すること。
`npm test` は合成マップ（`tests/.samples/`、実行のたびに生成）だけで完結し、常に緑であること。
実マップは消滅済み。実マップ専用の検証項目は `npm run test:compat`（`SAMPLES_DIR` に実マップのフォルダを指定）にだけ含まれる。
CI（`.github/workflows/ci.yml`）が `npm ci` → `npm test` → `npm run build` と、`dist` がソースと一致しているかを確認する。
`dist/app.js` は `js/` から `npm run build` で作る成果物。ソースが正で、dist だけを直さないこと。

読み取れること:
- **弱い側が勝つ判定の不具合は無い。** 戦力比3倍・5倍で弱い側は0%勝つ。1.5倍で弱い側が約2割勝つのは、番狂わせ（ノイズ）と、同戦力では防衛側が有利（攻撃側37%・防衛側43%）という設計どおりの動き。
- 戦力比3倍以上は強い側がほぼ必勝（ノイズが一様分布で上限があるため、合計の優勢度が約0.08を超えると番狂わせが起きない）。戦力比2倍は、勝ち75%・弱い側の逆転4%・膠着20%（決着した戦いだけで見ると、強い側が約95%）。
- 「兵力の壊滅」（`attrition`）は、通常の戦争では**ほぼ起きない**（敗者の損耗が動員兵力の3割に届かない）。民意の崩壊（`exhaustion`）は、民意が尽きた側があるときだけ起き、そのとき必ず尽きた側が降伏する。

**相談事項（数字を示して相談する、とされていた点）**
1. **全ての節を選んだ国が、同戦力の「節なし」の国に約96%勝つ。** 確定済みの上限（兵科±60%・攻め守り±25%）を入れてもこうなる。原因は上限値そのものではなく、`edgeOf` が「攻め − 守り」に0.5を掛けて優勢度へ足す点にある（守り+25% ＝ 優勢度 +0.125 ＝ 戦力2倍の優勢度 +0.06 の2倍）。作業用コピーでの感度（全ての節 vs 節なし、n=300）: 現状 約95% ／ 攻守の上限を±10%に 約96% ／ 攻守±25%のまま効き方を0.5→0.2に 約89% ／ 0.5→0.1に 約81% ／ 攻守の効果なしで兵科のみ±60% 約64%。つまり、上限を下げても効かず、**効き方（0.5）を下げるか、兵科の上限を下げる**のが効く。
2. **戦力比2倍の勝率が約75%で、「8割以上」に届かない。** 膠着（約20%）が大きいのが主因（`verdictOf` の幅0.015と、ノイズの大きさ）。`BALANCE.noiseAmp` を既定 0.18 → 0.135 にすると2倍で約86%、0.09 にすると2倍が100%で、1.5倍の膠着が24%に増える（弱い側の逆転は0%になる）。

どちらも、検証ツールの判定で「不合格」と出る（基準は緩めていない）。方針が決まれば、数値の変更だけで済む。

## 追加済み：反乱・分離（HoI4 風・いちばん新しい）

属州が離反すると、別の国家として成立し、軍が割れて元の国との内戦になる。理想は「補給や物資の細かい設定がない HoI4」なので、領土・都市・属州・軍の割れ方と、内戦という1つの戦争だけで表し、補給は持たない。

- `planDeclareIndependence`（`core/edit/sovereignty.js`）を、複数の属州をまとめて切り離せるように拡張（`provinceIds`、先頭が中心の属州）。新国家に `parentState`（分離元）を持たせ、`cause: "rebellion"` を主権ログに残す。年表は「反乱: ○○が△△から離反し…（内戦）」と書き分ける（平和的な独立は従来の文面）。
- `core/edit/rebellion.js`: `breakawayCandidates`（首都の属州・都市の無い属州は除き、首都から遠い順）／`pickBreakawayProvinces`（自然発生用に、属州の2〜4割を選ぶ。元の国に必ず属州が残る）／`planSplitArmy`（反乱側の領土にいる部隊はそのまま移り、残りの部隊からは領土の割合〈1〜4.5割〉の兵力を首都の「反乱軍」にまとめる。兵力の合計は変わらない）。

## テストで踏んだ落とし穴（同じ罠を踏まないために）

次チャットが同種の機能を追加する際、以下は過去に実際にハマった。

1. **`??` と `||` の混在は構文エラー。** `a ?? b || c` は書けない。
   `a ?? (b || c)` のように必ず括弧で明示する。
2. **`querySelector`と`getElementById`を混同しない。** このプロジェクトの
   `$()`ヘルパーは`getElementById`用。CSSセレクタを渡すバグを複数回起こした。
   CSSセレクタには`q()`（`querySelector`）を使う。
3. **`<input>`要素の値は`textContent`に含まれない。** `card.textContent.includes(name)`
   のようなテストは、名前が`<input value="...">`で表示されている場合は常に
   偽になる。`input.value === name`で判定すること。
4. **`render()`が要素を作り直すUIでは、クリック後に取得したDOM参照は古くなる。**
   `button.click()`の後、同じ`button`変数のプロパティを見ても更新されない。
   クリック後は改めて`querySelector`等でDOMから取り直すこと。
5. **Pythonの`str.replace`で`assert`が失敗すると、その回のファイル書き込みは
   一切行われない。** 複数の置換をまとめて1つの`open(...).write()`で書く
   スクリプトは、途中の`assert`で例外が起きると全体が失敗し、ファイルは
   一切変更されない（部分適用されない）。ドキュメント更新でこれを踏み、
   「前回書いたはずの内容が消えている」ように見える事象が実際に起きた。
   置換前に`grep`等で対象文字列の実在を確認してから流すこと。
6. **実データは公式仕様の「模範解答」ではない。** 2つのサンプルファイルは
   ユーザーが手動編集した痕跡があり（属州が国境沿いに薄い、宗教の保存値と
   実測がずれている等）、最初から矛盾を含む。「実データと一致しない」＝
   「自分の実装が間違っている」と早合点せず、まず矛盾が編集前から存在した
   ものか(`core/edit/integrity.js`のbaseline機構はこのために作った)を疑うこと。
