`.map` 形式の仕様は `MAP_FORMAT_SPEC.md` を見ること。ここでは重複を避け、

## 最優先：実ブラウザでの動作確認（何もかもこれ次第）

**この実装は Node.js + jsdom でしか動作確認していない。実ブラウザ（Edge）・実機
（Surface Go 4）では一度も動かしていない。** jsdom は Canvas 描画をしない偽の
コンテキストを使っているため、次のようなクラスのバグは自動テストが原理的に
検出できない：

- 実際の描画結果（色・線・文字のレイアウト崩れ、z-index、はみ出し）
- ポインタイベントの実ブラウザ差異（pointer capture の挙動、タッチとの相性）
- パフォーマンス（7603セルの地図でブラシを引いたときのカクつき、年次更新の重さ）
- `<dialog>` 要素の実際の見た目・フォーカストラップ
- CSS のレイアウト崩れ（特に `.wide-dialog` や `.regiment-units` の grid）

**次チャットが最初にやるべきこと**: `alterhistory.zip` を展開し、`index.html` を
実際にブラウザで開いて、以下を一通り操作し、気づいた不具合を直す。

1. 地図を開く → ズーム/パン → 色分け切替
2. 編集ツールで塗る・都市を置く・マーカーを置く → パネルで文章を書く
3. 時間バーで開始 → 数年待って人口が増えるのを確認 → 停止
4. 軍事パネルで部隊を編成 → 兵力を入力 → 別国の部隊を作って攻撃 → 結果を見る
5. 戦争タブで宣戦布告 → 講和条約で割譲 → 同盟タブで3カ国同盟を作る
6. 保存 → 保存したファイルを再度開いて、内容が引き継がれているか確認

## 未実装（要望のうち、まだ手を付けていないもの）

### 1. 地図の自動生成（最大の未実装部分）
地形・河川・気候・都市・道路・国家・宗教の生成は何も無い。現状は
「Azgaarで作った地図を読み込んで編集する」ことしかできず、ゼロから地図を
作ることはできない。これは当初の要望の中心の一つだったが、「編集を先に」
という指示で後回しにした経緯がある。着手する場合は `MAP_FORMAT_SPEC.md` の
「pack の形は保存されていない」節と `core/geometry.js` の grid→pack 再構築を
先に理解すること（生成順序に依存する）。

### 2. 日本語の名前生成
Azgaarの名前ベース方式（`namesbase`、`io/azgaar-reader.js` の
`parseNamesbase`）は読み書きだけ対応していて、**新しい名前を生成する機能が
無い**。都市追加時 (`core/edit/burgs.js` の `planAddBurg`) は毎回ユーザーが
手で名前を入力する必要がある。マルコフ連鎖等での生成ロジックは未着手。

### 3. 国家・宗教等の「ユーザー設定に基づく自動配置」
`core/edit/attributes.js` で技術水準等の自由記述属性は持てるが、その値を
読んで実際に地形やユニットを自動配置する仕組みは無い。全て手動配置。

### 4. 境界線・頂点そのものの手動編集
今の編集は「セル単位の塗り替え」（`core/edit/paint.js`）のみ。国境線を
ドラッグで直接動かすような、頂点単位の編集ツールは無い。
`core/geometry.js` の `applyVertexOverrides`（Azgaar形式のgraphOverride読み込み）
は実装済みだが、これは**読み込んだ値をそのまま適用するだけ**で、ALTERHISTORY
側から新たに頂点を動かす編集機能ではない。

### 5. 書き出し画像の凡例・スケールバー
画面上の凡例（サイドバー）はあるが、`io/exporter.js` で作るPNG/SVGには
凡例やスケールバーが焼き込まれない。

### 6. 重い処理のWeb Worker化
`.map` の読み込み・パース・年次更新は全てメインスレッドで同期実行される。
7603セルの地図で数百ミリ秒かかることを確認済み（`tests/reader.test.mjs`参照）。
実ブラウザで体感的に重ければ、ここが原因になりやすい。

### 7. 将来構想：軽い都市建築＋徒歩視点
ユーザーの将来要望。今回のCanvas 2Dベースの2D地図とは全く別のレンダリング
方式（3D or 2.5D）が必要になる規模で、着手していない。優先度は低い想定。

## 実装したが「仮置き」の数値（実データに基づかない）

以下は「動くようにするため」に置いた値で、実データや理論的根拠に基づかない。
プレイしてバランス調整が必要になる可能性が高い。

### 経済成長（`core/sim/economy.js`）
```
年間人口成長率 = 0.6%（技術Lv1） 〜 2.1%（技術Lv10）、ロジスティック成長
産業力係数     = 0.05（技術Lv1） 〜 0.86（技術Lv10）、人口1000人あたり
人口の上限     = 初期人口の3倍（固定）
```
技術水準は国家に `techLevel`（1〜10、既定3）として保持されるが、**技術水準を
上げる手段がUIに無い**（`core/edit/attributes.js` 経由の自由記述属性とは別物）。
現状は`techLevel`を直接編集するUIが存在しない。技術水準を変える場合は
コンソールから `map.pack.states[id].techLevel = 5` のように直接いじるしかない。
**ここは次チャットで真っ先にUI化すべき欠落点。**

### 兵科の戦闘力係数（`core/sim/units.js`）
```
歩兵1（人）: power=1        機甲(台): power=8     航空(機): power=15
海軍(隻): power=40          特殊部隊(人): power=4  先端技術(人): power=6（技術Lv6以上）
核(発): power=500（技術Lv9以上）
```
歩兵を1とした相対値。海軍が1隻=歩兵40人相当、核が1発=歩兵500人相当という
比率は感覚で決めたもの。ドクトリン補正（`DOCTRINES`）も同様に仮置き。

### 戦闘判定（`core/sim/battle.js`）
```
勝率決定 = 戦力比較 × 乱数(0.85〜1.15)
勝者の損耗 = 3%〜12%（戦力差が大きいほど小さい）
敗者の損耗 = 15%〜40%（戦力差が大きいほど大きい）
```

### 徴兵ペース（`core/sim/military.js` の `planAnnualConscription`）
年間の徴兵数は `(人口/1000) × (rural+urban係数) × 0.15` + `産業力配分`。
0.15という係数は「緩やかに増える」ことだけを狙った仮の値。

## 設計上の既知の制約（バグではなく意図的な割り切り）

これらは `ARCHITECTURE.md` にも書いてあるが、次チャットが「バグでは」と
誤解しないよう改めて明記する。

- **`state.rural`/`state.urban`（経済モデルの人口）と、セル単位の`pop`配列は
  もう一致しない。** 年次更新は国家の集計値だけを書き換え、セルには反映しない。
  `core/edit/integrity.js` の `skipEconomyChecks` オプションはこのズレを
  意図的に無視する設計。もし「セル単位でも人口を可視化したい」という要望が
  出たら、これは作り直しが必要（現状のモデルでは表現できない）。
- **戦闘に勝っても国境は動かない。** 占領は概念として存在せず、講和条約でしか
  領土は動かない（ユーザー要件どおり）。「勝ったのに何も変わらないように見える」
  という問い合わせが来たら、これは仕様。
- **属州は分割譲渡できない。** `core/edit/wars.js` の講和は属州を丸ごと移すか、
  属州の無い地域（フラッドフィルで作った塊）を移すかの二択。属州の一部だけを
  切り出す機能は無い。
- **月の進行はUndoできない。年またぎで起きる人口/徴兵の変化はUndoできる。**
  `app/time-actions.js` 参照。意図的な設計判断。

## UIの既知の粗さ（動くが磨けていない）

- 軍事パネルは、部隊を1つ編集するたびに `render()` が呼ばれてDOM全体を
  作り直す（`js/ui/panels/military-panel.js`）。部隊数が多い国家（実データで
  最大5部隊程度は確認済みだが、ユーザーが数十個作ると）で、入力のたびに
  画面全体が再構築されるため、フォーカスが失われたり、カクついたりする
  可能性がある。実ブラウザで要確認。
- `alert()` / `confirm()` / `prompt()` をそのまま使っている箇所が複数ある
  （部隊解散の確認、都市名の入力など）。ブラウザ標準ダイアログなので動作は
  するが、見た目が浮く。UIに合わせた自前のダイアログに置き換える余地がある。
- 部隊の「対象を選択中…」という攻撃対象選択モードは、モーダル的な状態管理を
  していない。パネルを閉じずに他の操作をすると、選択中状態のままになる。
  意図的にキャンセルする手段（Escキー等）が無い。

## テストで踏んだ落とし穴（同じ罠を踏まないために）

次チャットが同種の機能を追加する際、以下は過去に実際にハマった。

1. **`??` と `||` の混在は構文エラー。** `a ?? b || c` は書けない。
   `a ?? (b || c)` のように必ず括弧で明示する。
2. **`querySelector`と`getElementById`を混同しない。** このプロジェクトの
   `$()`ヘルパーは`getElementById`用。CSSセレクタを渡すバグを複数回起こした。
   CSSセレクタには`q()`（`querySelector`）を使う。
3. **`<input>`要素の値は`textContent`に含まれない。** `card.textContent.includes(name)`
   のようなテストは、名前が`<input value="...">`で表示されている場合は常に
   偽になる。`input.value === name`で判定すること。
4. **`render()`が要素を作り直すUIでは、クリック後に取得したDOM参照は古くなる。**
   `button.click()`の後、同じ`button`変数のプロパティを見ても更新されない。
   クリック後は改めて`querySelector`等でDOMから取り直すこと。
5. **Pythonの`str.replace`で`assert`が失敗すると、その回のファイル書き込みは
   一切行われない。** 複数の置換をまとめて1つの`open(...).write()`で書く
   スクリプトは、途中の`assert`で例外が起きると全体が失敗し、ファイルは
   一切変更されない（部分適用されない）。ドキュメント更新でこれを踏み、
   「前回書いたはずの内容が消えている」ように見える事象が実際に起きた。
   置換前に`grep`等で対象文字列の実在を確認してから流すこと。
6. **実データは公式仕様の「模範解答」ではない。** 2つのサンプルファイルは
   ユーザーが手動編集した痕跡があり（属州が国境沿いに薄い、宗教の保存値と
   実測がずれている等）、最初から矛盾を含む。「実データと一致しない」＝
   「自分の実装が間違っている」と早合点せず、まず矛盾が編集前から存在した
   ものか(`core/edit/integrity.js`のbaseline機構はこのために作った)を疑うこと。
