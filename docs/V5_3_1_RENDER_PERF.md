# v5.3.1 描画性能の修正（25万セルの初回表示）

障害: 25万セルの新規世界を作ると、世界生成は数秒で終わるのに、地図が表示されるまで数十秒〜数分かかる（Edge 実機）。
計測データ: `docs/perf-v531-render.json`。再現: `tests/perf/browser-render-bench.mjs`、`tests/e2e/render-perf.e2e.mjs`。

## 1. 原因（測定で確定した範囲）

**セルの多角形パスを作るときの `closePath()` が、1本のパスに輪郭が増えるほど遅くなる（輪郭数の二乗）。**

同じ頂点を、1本の `Path2D` に積む時間（ヘッドレス Chromium 153）:

| 1本に積むセル数 | closePath あり | closePath なし |
| ---: | ---: | ---: |
| 2,000 | 35 ms | |
| 5,000 | 224 ms | |
| 10,000 | 867 ms | |
| 25,835 | **5,713 ms** | **11 ms** |

- キャンバスのパス（`ctx.beginPath()` で積む場合）も同じ（5,612 ms）。SVG 文字列から `Path2D` を作る場合は 66 ms。
- 塗りつぶし（`fill()`）は、閉じていない輪郭を自動で閉じる（Canvas の仕様）。`addCellPath` の呼び出し元（地形・政治・ゾーン・強調表示）は、どれも直後に `fill()` するだけで、`stroke` には使わない。だから `closePath()` を外しても結果は変わらない（旧方式と1画素も違わないことを `tests/v531-render.test.mjs` で確認）。
- 全体表示では、地形のパスが 25 万セル分（頂点約 150 万）になる。さらに、継ぎ目の両側のコピー（-1 と +1）は、見える所だけを毎回キャンバスのパスに積み直す。そのすべてに closePath が付いていた。

### 調査報告書の計測が原因を示せなかった理由

- 「Path2D の 1% 標本の構築時間（2.85 秒）から外挿」は、線形に増えると仮定した見積もり。二乗で増えるので、1% では 35 ms 程度で、全体の遅さが見えなかった。
- 「`fill()` 75 回で 33 ms」は、Chromium の Canvas 2D が命令を記録するだけで、塗りは後でまとめて行うため。塗り終わりまで待たずに測った値で、塗りの時間は別の所に出る。
- 「Canvas のメソッドを何もしない関数にした `drawScene` が 443 ms」は、その状態では closePath も呼ばれないため。

## 2. 修正内容（ファイル別）

| ファイル | 変更と理由 |
| --- | --- |
| `js/render/layers/terrain.js` | `addCellPath` から `closePath()` を外した（根本原因）。地形のパス構築・塗り・分類・近傍描画の時間と件数を計測できるようにした |
| `js/render/layers/politics.js` | 国家・州の塗りの、パス構築と塗りの時間を計測できるようにした |
| `js/render/profile.js`（新） | 段階別の時間の集計。通常は合計だけ。`sync` で塗り終わりまで待つ（計測専用） |
| `js/render/scene.js` | コピーごと・層ごとの時間を集める |
| `js/render/renderer.js` | `requestRender()` が約束を返す。要求より後のタイルを描いて貼り終えたときに解決し、失敗は拒否で伝える。`lastRender` に準備・シーン・貼り付け・画面表示までの時間と層別の内訳 |
| `js/app/actions.js` | 地図を採用しただけでは「処理中」を消さず、初回の描画が終わってから消す。描画の失敗は成功扱いにせず error に出す。世界生成・地図変換・採用・描画（タイル・シーン・貼り付け）を別項目で通知と console に出す |
| `js/render/perf-report.js`（新）・`js/main.js` | `alterhistory.perf()`: 実機で、塗り終わりまでの時間を、既定キャンバスと CPU キャンバスで比べる |
| `scripts/build.mjs`（新）・`package.json` | ビルド識別子と `dist/build-info.json`（版・各ファイルの SHA-256）。`npm run build:check` |
| `js/version.js`・`js/ui/settings-windows.js` | 5.3.1。「このアプリについて」にビルド識別子 |

変えていないもの: 地図データ・セル数・地形・政治レイヤー・極域/継ぎ目の描画内容・世界生成・保存形式。ローディング表示を早く消す変更はしていない（逆に、描画が終わるまで消さない）。

## 3. 修正前後（同じ環境）

環境: ヘッドレス Chromium 153（`@sparticuz/chromium`）・1コア・GPU はソフトウェア模擬・画面 1280×853。**Edge 実機の値ではない。**

全体表示のタイル描画（命令を並べる側 = JS の時間。ms）:

| セル数 | 修正前 初回 → 2回目 | 修正後 初回 → 2回目 |
| ---: | ---: | ---: |
| 50,000 | 9,088 → 3,166 | 274 → 85 |
| 100,000 | 34,565 → 11,723 | 357 → 161 |
| 250,000 | 約 224,000（アプリの初回。生成完了から最初のフレームまで 229,984） | アプリの初回 621〜652（繰り返し 615 / 450 / 447） |

修正前は二乗で増える（5万→10万で約 3.8 倍）。修正後はほぼ線形。

25 万セルの新規世界（実際のアプリで、クリックから描画完了まで）: 約 230 秒 + 生成 6 秒 → **合計 6.1〜6.4 秒**（うち生成 約 4〜5 秒・タイル描画 約 0.65 秒）。「地図を描画中…」を経て、描画が終わってから処理中が消える。

16 倍拡大（ms, JS）: 修正前 299 / 316 / 212 → 修正後 185 / 72 / 52（拡大は元々遅くなかった）。

描画中の long task（実アプリ・25 万セル）: 世界生成の中間で 0.5〜1.7 秒が数回。描画そのものでは 1 秒を超える塞がりは出ない（`docs/perf-v531-render.json`）。

## 4. 未確定・実機（Edge）で確認してほしいこと

1. **closePath の二乗が Edge 実機でも原因か**: Edge は Chromium なので同じ構造のはずだが、実機の Edge では未測定。Edge の通常実行（DevTools を開かない）で 25 万セルの新規世界を作り、「地図を描画中…」が出てから消えるまでの時間を測る。console の `[世界生成]` に、生成・地図変換・採用・描画完了の内訳が出る。
2. **塗り終わりまでの時間（GPU か CPU か）**: このヘッドレス環境では、既定のキャンバス（GPU を模擬）の塗り終わりが、初回 91.5 秒・2回目 13.5 秒・3回目 1.1 秒と大きくばらついた。CPU キャンバスは毎回約 1.1 秒。実機の GPU で同じ差が出るかは未確認。コンソールで **`await alterhistory.perf()`** を実行し、表の「既定」と「CPU」の「塗り終わりまで(ms)」を見る。「既定」が数秒を超えて「CPU」が速い場合は、タイルのキャンバスを CPU 描画（`willReadFrequently`）にする修正が必要（1行）。実機の数値なしには変えない。
3. 5 秒以内（25 万セル・全体表示）の判定は、上の `perf()` の「合計(ms)」と、画面に地図が出るまでの体感で行う。このヘッドレス環境の値（CPU キャンバス 約 1.4〜1.6 秒）を実機の合格値として流用しない。
4. `renderer.lastRender.presentMs`（貼り付け後に次のフレームが出るまで）は、フレームの表示時刻であって、塗りの完了時刻ではない（塗りが別プロセスで遅れて終わる場合、これは小さく出る）。塗りの完了は `perf()` で測る。

## 5. 再現手順

```
npm run build
node tests/perf/browser-render-bench.mjs 250000 out.json   # 実ブラウザ（Chromium）の before/after 用
node tests/e2e/render-perf.e2e.mjs                         # 25万セルの新規世界（合否つき）
npm run build:check                                        # dist がソースと一致するか
```
Edge 実機: アプリの画面で F12 → コンソール → `alterhistory.build`（版とビルド識別子）／`await alterhistory.perf()`。
